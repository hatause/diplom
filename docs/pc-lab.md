# Практикум ПК и Windows

## Интеграция

Маршрут `/pc-lab` доступен гостям и зарегистрированным пользователям. Ссылки находятся на главной странице и в боковом меню; карточки результатов — в обзоре и профиле.

React-оболочка в `frontend/src/features/pc-lab/` отвечает за авторизацию, локальный черновик, запросы API, баллы и статус синхронизации. Стенд находится в `frontend/public/pc-lab-assets/` как отдельные HTML/CSS/JS в same-origin iframe. Его CSS изолирован от сайта. Внутри встроен второй same-origin iframe `/pc-lab-viewer.html`: отдельная точка входа Vite для Three.js. Исходные SVG служат резервным режимом, если WebGL недоступен. Фрейм не получает токен авторизации. Обе стороны проверяют `origin` и `source` сообщений; входящий прогресс нормализуется по разрешённым значениям.

Каталог ресурсов отличается от маршрута React, чтобы Nginx не перенаправлял `/pc-lab` на статический `index.html`. Права публичных файлов нормализуются в Docker-образе для чтения рабочими процессами Nginx, независимо от umask сервера. Нехешированные ресурсы стенда имеют `Cache-Control: no-cache`; сборочные хешированные JS/CSS сайта продолжают кешироваться.

Поздние требования о пяти полных модулях применены вместо ранних временных заглушек. По следующему запросу пользователя модели полностью пересобраны в объёмной геометрии. Использованы принципы Anatomy: узнаваемые детали, крепления, слои, материалы, плавная разборка и проверка крупных планов. Свободное вращение и определение видимости реализованы Three.js/WebGL; SVG-аудит Anatomy к этому рендереру не применяется.

## Функции и исправления

- Восемь объёмных моделей: CPU, GPU, DIMM, NVMe, ATX-плата, кулер, БП, корпус. Геометрия в `hardware/models.ts`, описание в `hardware/catalog.ts`, камера/сцена/события в `hardware/viewer.ts`. Каждая модель содержит более 100 геометрических деталей, 3–4 разборных узла, выбор отдельного слоя и прозрачность. Модели учебные, без гарантии масштаба или соответствия конкретному изделию.
- Общий стенд: клик по видимому компоненту или списку запускает выдвижение и открывает отдельную модель; кнопка возврата восстанавливает компьютер. Два DIMM стоят на плате; CPU, кулер, SSD и GPU ориентированы относительно своих разъёмов. Вращение мышью/касанием/стрелками, масштаб колёсиком/кнопками, виды спереди/сзади/сверху, тёмный и светлый фон. Инспектор показывает фактическую версию BIOS и состояние ОС.
- Восемь устанавливаемых элементов, проверки зависимостей и разъёмов, подсказка, автошаг и повторная попытка. Ray casting отдаёт приоритет выбранному пересекающемуся слоту. Под сценой есть доступные с клавиатуры кнопки посадочных мест; проверки совместимости те же. Для резервного SVG выбранная зона поднимается над соседними областями клика.
- BIOS: POST/DEL, UEFI, M-Flash, выбор ROM, запись SPI и v2.40. Повторный запуск сбрасывает завершение.
- Windows: TPM/Secure Boot (два решения), Intel VMD (два решения), MBR/GPT, OOBE, недостаточный объём системного раздела и цикл загрузки с USB. Два мини-теста по два вопроса проверяют резервное копирование, UEFI/GPT, EFI и драйверы. Неверный выбор объясняется и учитывается, продолжение доступно после верных ответов. Три редакции, язык/регион/клавиатура, размеры C/D, три обязательных драйвера, рабочий стол и итоговая конфигурация.
- Переключение вкладок сохраняет сборку и останавливает активные таймеры. Прерванную запись BIOS/Windows можно запустить снова. Завершённые этапы восстанавливаются после перезагрузки.
- Выключенный чекбокс неисправности не считается её решением. Повторное включение неисправности возвращает установщик на соответствующий этап и снимает ранее полученную отметку этой неисправности.
- Панель установщика размещена перед 3D-сценой и не закрывает аппаратные компоненты. Адаптивные сетки, focus-индикаторы, reduced-motion, остановка CSS-анимаций при скрытии вкладки.

Команды выполняются только в симуляции. Оценка предназначена для самостоятельной практики, не для защищённого экзамена: сервер проверяет данные и вычисляет баллы, но события практикума сообщает браузер. Исходный вымышленный код TPM заменён явно учебным `LAB-TPM`. Старые сценарии LabConfig/OOBE BYPASSNRO помечены как зависящие от версии установщика, со ссылками Microsoft. Для DiskPart объяснено действие `clean` на настоящем диске.

## API и хранение

- `GET /api/v1/pc-lab/progress` — сохранение текущего пользователя или нулевой результат.
- `POST /api/v1/pc-lab/progress` — частичное обновление, серверный расчёт оценки и новая ревизия.
- Таблица `pc_lab_progress`: уникальная связь с User, каскадное удаление, разобранные модели, сборка/ошибки, BIOS, Windows, решённые неисправности, раздел C, состояние возобновления, ревизия и даты.
- Неверные значения и лишние поля отклоняются. Пользователь не передаёт чужой ID или готовый балл.
- При отправке клиент передаёт `revision`. Транзакционная блокировка строки пользователя сериализует одновременные записи; устаревшая ревизия получает 409. UI предлагает явно заменить локальный черновик серверной версией.
- Автосохранение с задержкой 350 мс; таймаут запросов прогресса 8 секунд, чтобы зависший сервер не блокировал локальный практикум. До ответа сервера изменения остаются в localStorage; ошибки сети не уничтожают черновик. Есть повторное подключение. Гостевой ключ и ключи пользователей раздельные: результаты чужой сессии не импортируются автоматически.

Оценка: `floor(15 × число_разобранных / 8)` + сборка `max(15, 30 − 2 × ошибки)` при завершении + BIOS 20 + Windows 35 при завершении, решении всех шести неисправностей и четырёх верных ответах в двух мини-тестах. Ответы повторно проверяются сервером. Зачтено от 80. `completed_at` появляется только при завершении всех четырёх разделов практикума.

Новая программа имеет `resume.curriculum_version = 2`. Сохранения без этого поля читаются как v1 и сохраняют прежние баллы (четыре неисправности). «Перезапустить этап» начинает v2; сервер не позволяет понизить версию v2 частичным обновлением. Ответы, ошибки диагностики и тестов хранятся в существующем JSON `resume`, новые SQL-миграции не нужны.

## Производительность 3D

Геометрия собирается один раз при выборе модели; повторяющиеся детали объединяются по материалу и разборному узлу. Анимация меняет трансформации групп. Камера вписывает габариты конечной позы, включая разобранные слои; уменьшенные экраны учитываются через aspect ratio. DPR ограничен 1.5. Рендер работает по запросу, прекращается в покое, вне экрана и на скрытой вкладке; при `prefers-reduced-motion` переходы мгновенные. При замене модели геометрия, материалы и текстуры освобождаются. Ни один из фреймов не получает токены.

## Проверки

- `npm run build --prefix frontend` — TypeScript и Vite. Сохраняется предупреждение Vite о размере существующего общего bundle; модуль практикума загружается лениво.
- `npm run lint --prefix frontend` — без ошибок и предупреждений.
- 69 Python-тестов, включая новые проверки оценки, авторизации, изоляции пользователей, частичного сохранения, валидации, конкурентной записи и каскадного удаления. Запускать с `RUN_DB_TESTS=1 RUN_SCHEDULE_DB_TESTS=1` только на отдельной тестовой БД `schedule_test_*`.
- `scripts/check-pc-lab.cjs` — 38 браузерных проверок через UI. Требует Playwright (`PLAYWRIGHT_MODULE` при внешней установке), API и Vite с отдельной тестовой БД. По умолчанию `http://localhost:5174`; внешние адреса запрещены. Временная учётная запись остаётся только в этой удаляемой тестовой БД.
- `scripts/check-pc-hardware.cjs` — 61 проверка: восемь моделей, вращение, разборка, прозрачность, изоляция слоёв, извлечение всех компонентов, реальные pointer-клики, клавиатура, 390/320 px, отсутствие непрерывного рендера и режим без WebGL. `LAB_SCREENSHOT_DIR` сохраняет снимки для визуальной проверки.
- Визуально проверяются собранные/разобранные модели в обеих темах, общий ПК, мобильные экраны и крупные планы.

## Обновление базы и откат

Обновление 3D/программы v2 не меняет схему БД: повторно применять SQL ниже не нужно.

Для первоначальной установки практикума сначала сделать резервную копию PostgreSQL, uploads и серверной конфигурации. Собрать новые backend/frontend, затем один раз применить `python_backend/migrations/20261015_pc_lab_progress.sql` через `psql -v ON_ERROR_STOP=1`, после чего обновить контейнеры. Миграция транзакционная, только добавляет таблицу и не изменяет существующие данные. На новой локальной тестовой БД допустим `prisma db push`.

Не применять `--accept-data-loss` и не сбрасывать базу. При откате вернуть предыдущие образы приложения; новую таблицу можно оставить, старому приложению она не мешает. Повторный запуск SQL на уже мигрированной БД намеренно завершится ошибкой вместо скрытого изменения схемы.
